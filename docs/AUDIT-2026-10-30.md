# Pre-build Repository Audit — 2026-10-30

Read-only scan requested before building the tiered-enforcement work. Covers dead code,
accreting layers, bugs, workflow, pipeline, methodology, and SRE. Every finding cites evidence;
nothing here changes code. Severity: **Critical / High / Medium / Low**.

## Headline

The single most important finding ties six sub-findings together: **CI's quality gate does not
inspect the shipped product.** The MCP server lives in `mcp/ai_rule_learning_mcp/`, but `ruff`
excludes `mcp/`, `mypy` checks a different tree (`src/`), and coverage measures `src/`. CI is
green while the real code is unlinted, untyped, and uncovered. Three latent errors and 75 lint
findings in the shipped package are invisible to the pipeline. Fix the gate before trusting any
"green" as evidence of quality.

## A. Dead code & parallel layers

- **A1 [High] Two parallel codebases.** `src/` (3,135 lines: `core/interceptor`,
  `core/rule_engine`, `core/alignment_sensor`, `adapters/`, `services/`, `models/`) is a second,
  older architecture. It is **not imported by the shipped product** — `grep` finds zero imports
  of `src` inside `mcp/ai_rule_learning_mcp/`; only `scripts/*.py` import it. The product is
  `mcp/ai_rule_learning_mcp/` (9,101 lines). Two architectures for one tool.
- **A2 [High] Enforcement channel is a disconnected dead-end.** `enforcement.classify/enforce`
  are reachable only via `cli.py:cmd_enforce` (`ai-rule-learning enforce <file>`). `server.py`
  never imports or calls them, so the live agent loop never enforces. (See `docs/INVENTORY.md`.)
- **A3 [Medium] Seven inert detector stubs.** `enforcement.py` REGISTRY has 9 structural
  checks; 7 are `implemented=False, detect=None` (`no_print`, `no_else`, `type_hints`,
  `snake_case`, `short_funcs`, `pathlib`, `single_block`). They classify as "structural" and
  then do nothing (`enforce` returns `pending`).
- **A4 [Medium] Satellite modules of unverified liveness.** `community.py` (518 lines) backs
  `update_community_knowledge`, but P3 retired the `arl-community-rules` bucket — confirm it is
  not already partly dead. Same audit owed for `scheduler`, `skills`, `memory`, `analyzer`,
  `kpi`, `metrics`, `clustering`, `similarity`, `dataset`.

## B. Accreting layers

- **B1 [High]** Two rule systems stacked in the live inject path: `load_active_rules()`
  (learned) **plus** `RuleCatalog.select()` (130 catalog defaults), merged and padded to 10 in
  `server.py:get_guardrail_rules` (≈940–971). Every session's prompt mixes both sources.
- **B2 [High]** The `src/` vs `mcp/` split (A1) is the deepest layer accretion: the same
  concepts (catalog, gap_detector, rule engine) exist in both trees.
- **B3 [Medium]** 21 MCP tools are exposed to every session; each tool schema costs tokens in
  the tool list before any rule is injected. The core loop needs ~2–3 of them.

## C. Bugs

- **C1 [Critical] Quality gate aimed at the wrong tree.** `pyproject.toml`:
  `[tool.ruff] exclude = ["space/", "mcp/", "study/", ...]` (shipped pkg excluded);
  CI `mypy src` (legacy tree); `addopts = "--cov=src"` (legacy tree). Result: the product is
  never linted/typed/covered by CI. `ruff check mcp/` → **75 errors**; `mypy mcp/...` →
  **3 errors**; both invisible to CI.
- **C2 [Medium] Latent type errors in shipped code.** `enforcement.py:82`
  (`body[0].value.value` — attribute access mypy cannot verify after a `getattr` guard;
  defensive but flagged) and `clustering.py:95` (sort key typed `object`). Low runtime risk,
  but exactly what a correct gate would catch.
- **C3 [Medium] Extraction misroutes to enforcement (verified by live probe).** `distill`
  produces text that the keyword `classify` cannot match: "Return the value instead of
  **printing** it" misses the `print(` keyword → SOFT; F10's rule body becomes the complaint
  ("You wrote explanations around the code"), not the directive. Net live enforcement coverage:
  2 of 10 families.
- **C4 [Medium] `record_feedback` mutates tracked files with no confirmation.** A live call
  from a repo root rewrote five version-controlled config files (incl. `CLAUDE.md`) via
  cwd-based config detection, while `dry_run` reported "no agent config files changed." The
  write surface is wider and quieter than the dry-run message implies.
- **C5 [Low] 59 broad `except Exception` / bare excepts in the shipped package** silently
  swallow failures (e.g. `enforcement._fix_comments`, `distill`), masking errors from any
  observability.

## D. Workflow (developer)

- **D1 [High] The documented gate gives false assurance.** `CLAUDE.md` §2.4 prescribes
  `ruff check .`, `mypy src`, `pytest` — which match CI and therefore inherit C1: following the
  documented workflow does **not** check the product. The claimed "coverage ≥ 80%" is also not
  enforced (no `fail-under` in `pyproject.toml` or CI) and measures `src/`.
- **D2 [Low] Branch/PR hygiene.** A single branch is reused across many squash-merged PRs
  (force-with-lease each cycle); PR #305's title/scope has drifted as commits were added. Works,
  but the PR no longer describes its contents without the updated body.

## E. Pipeline (CI/CD)

- **E1 [Critical]** = C1 (gate scope). The most impactful pipeline fix.
- **E2 [Medium] Coverage reported but not gated.** No `--cov-fail-under`; a coverage drop would
  not fail CI.
- **E3 [Low] Version drift.** Root `pyproject.toml` is `ai-rule-learning` **0.1.0**; shipped
  `mcp/pyproject.toml` is `ai-rule-learning-mcp` **0.2.7**. `publish-mcp.yml` bumps only the
  latter. Two version numbers for one project invite confusion.
- **E4 [Info] Otherwise mature.** `deploy-space.yml` (auto-deploy to HF on push to main),
  `publish-mcp.yml` (tag-triggered PyPI, `twine check`, trusted publishing), weekly `security`
  (Gitleaks + `npm audit`), daily `semgrep`, commitlint, markdownlint, Telegram failure alerts.
  The scaffolding is good; it is pointed at the wrong Python tree.

## F. Methodology

- **F1 [Critical]** The measurement feeding "quality" decisions is invalid for the product (C1).
  This undermines any claim derived from CI being green.
- **F2 [Medium] Effectiveness study is sound but narrow.** Pre-registered, placebo-controlled,
  deterministic oracle — genuinely good. But one weak model (`deepseek-flash`), learned rules
  equivalent to plain text (E ≡ D), and real over-application. Already documented in
  `study/RESULTS.md` and `docs/ACCEPTANCE.md`; restated here for completeness.
- **F3 [Medium] Doc drift.** `SRE.md` is marked "Approved / Active Production Baseline" for
  **v0.3.0**, a release not yet cut, and describes a 4-tier Cloudflare topology whose community
  path was partly retired (P3). Docs describe an intended state, not the current one.

## G. SRE

- **G1 [Medium] Topology doc vs reality.** `SRE.md`'s relay/aggregator/public-catalog tiers
  need reconciling with what is actually deployed after the P3 teardown.
- **G2 [Medium] Error masking.** The 59 broad excepts (C5) mean failures in enforcement,
  distillation and config writes are swallowed with no structured log or metric — contrary to
  the observability policy in `CLAUDE.md` §1.4. There is no health/readiness signal for the
  local MCP node.
- **G3 [Low] Alerting present.** CI failure → Telegram is wired. `kpi.py`/`metrics.py` exist but
  their liveness from the live path is unverified (A4).

## Suggested order (not done here; for ratification)

1. **Fix the gate (C1/E1/D1/F1) first** — point `ruff`, `mypy`, coverage at
   `mcp/ai_rule_learning_mcp`; add `--cov-fail-under`. Without this, no later "green" is
   evidence. This precedes even Phase 1.
2. Decide `src/` fate (A1/B2): keep as a separate supported package or delete — it should not
   sit unlabelled beside the product.
3. Then the planned Phase 1 (wire enforcement + implement the 7 detectors), under the
   now-trustworthy gate.
4. Satellite audit (A4) before Phase 3, per the complexity budget (`docs/ACCEPTANCE.md` §10).
